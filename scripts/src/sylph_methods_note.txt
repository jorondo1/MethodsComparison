sylph classification rate and read counts: methods note (to validate with the sylph authors)

Methods paragraph (draft)
Samples were profiled with sylph (v[x.x.x]) using --estimate-read-counts, which also turns on estimation of the unknown sequence fraction (-u). sylph reports no unclassified category in its output. Each sample's classification rate was therefore taken from the profiling log ("% of reads detected in database"): the fraction of the sample's bases covered by the detected genomes. With --estimate-read-counts, the estimated count of each genome is coverage x genome size / mean read length x classification rate. The first three terms already estimate the reads from that genome, so the extra factor makes a sample's counts sum to about rate^2 x total reads instead of rate x total reads. We therefore divided each sample's counts by its classification rate. This rescales each sample by a constant, so relative abundances within a sample are unchanged.

Rationale / evidence
- Source: sylph src/contain.rs, profile, estimate_read_counts branch:
  seq_abund = final_est_cov * gn_size / mean_read_length * bases_explained
  where bases_explained (estimate_covered_bases) = sum(gn_size * final_est_cov) / total sample bases, i.e. the logged classification rate.
  Summed over genomes: sum(counts) = (covered bases / read length) * rate = rate^2 * total reads.
  mean_read_length is per mate for paired reads, so counts are reads (mates), not pairs.
- Empirical check (Maple, sample 1_1_WGS_20250513, RefSeq_20250528 c200 db, ~16.2 M reads):
  rate = 0.076, sum(counts) / reads = 0.005, rate^2 = 0.006.
  The counts match rate^2 x reads, not rate x reads.
- Caveat: sylph rounds counts before this scaling, so very small counts can't be fully recovered (e.g. a 0 stays 0).

Question for the authors
Is the "* bases_explained" factor in the --estimate-read-counts branch intended? If it is, what do the counts represent? If not, is dividing by the logged "% of reads detected" the right correction?
